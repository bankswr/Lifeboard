# Android home-screen widgets (phase 8)

2026-10-17, agent (Claude). Built as agreed in docs/PLAN.md phase 8; verified on the
`fitapp_test` emulator (Android 16).

## How it fits together
- `src/core/widgets.ts` builds the snapshot: per widget a title, the page a tap opens and
  display-ready rows (title, sub line, right-hand value, style; list rows carry `itemId` and
  `done`). Pure builders per widget plus `widgetSnapshot(db)`; `test/widgets.test.ts`.
  Times are fixed points ("Tue 3:00 PM"), never countdowns, so a widget stays right between
  updates. Exposed as `api.getWidgetSnapshot`.
- `src/app/widgets.ts` (phone only): writes the snapshot JSON to shared preferences
  (`lifeboard_widgets` / `snapshot`) through **capacitor-widget-bridge** (MIT, Capacitor 8,
  last release 2026-03), then asks the five providers to redraw. Reuse decision: it does
  exactly the hand-over (set/get/remove a preferences string, redraw registered providers),
  so no Lifeboard plugin was written for it.
- When the snapshot is rebuilt: app start (after updates and reminders), every phone API
  call that isn't a read (`/^(get|list|analyze|recent|daily)/`, debounced 1 s), after each
  LAN sync, and on resume.
- Native (`android/.../widgets/`, Java to match MainActivity and GoogleAuthorizationPlugin):
  `RowsWidget` draws any part of the snapshot as a header + scrolling rows with
  `RemoteViewsCompat` collection items (`androidx.core:core-remoteviews:1.1.0`; no
  RemoteViewsService needed, works back to API 24). Five subclasses only name their key.
  Colors are the app's theme tokens, copied by hand.
- Taps open `lifeboard://open/<page>` (intent filter on MainActivity); `@capacitor/app`'s
  launch URL / `appUrlOpen` sets the hash.

## Lists widget
- **Choosing the list:** a configuration screen (`ListsWidgetConfigure`) when the widget
  is placed, listing the snapshot's to-do lists; reconfigurable from the launcher. If no
  list was chosen (app never opened) or the list was deleted, it shows the first list.
  Prototype lists are left out: their checkboxes select items to copy.
- **Ticks:** a row tap is a broadcast back to `ListsWidget`, which stores `{itemId: done}`
  under `ticks` and redraws at once with the queued state (crossed out). The app applies
  the queue at start (after `clearCheckedItems`, so widget ticks show crossed out in the app
  and clear at the next load like app ticks) and on resume, through `setTodoItemDone`,
  so they sync normally. Native code never writes the database.
- **Known small race:** the app reads the queue, removes it, then applies it. A tick made
  in the instant between reading and removing would be lost (the widget would then redraw
  it unticked at the next snapshot). Accepted: the window is milliseconds while the app is
  starting or resuming.

## Add button and Calendar task ticks (2026-10-18, user-agreed)
- **Lists widget "+"** (header, `ListsWidget.decorateHeader`; the button is `widget_add` in
  `widget_rows.xml`, hidden on other widgets): opens `ListAddActivity`, a dialog-themed
  Activity (`WidgetDialog` style: Theme.Material.Dialog with the app's green accent) over
  the home screen, with a text box and Cancel/Add; the keyboard opens with it. Add queues
  `{listId, text}` under `adds` (a JSON array) for the list the widget shows
  (`ListsWidget.shownList`, the same fallback as drawing) and redraws: the queued item
  appears after the open items with "Added when Lifeboard next opens" and no tick box (it
  has no id until the app adds it).
- **Calendar task ticks:** today's open task rows carry `itemId` (the task id) and
  `done: false` in the snapshot (`calendarWidget`), so they get the same tick box as list
  rows. Tapping queues `{taskId: done}` under `taskTicks`, redraws crossed out; tapping a
  crossed-out task queues an untick (same toggle as the Lists widget). Once the app applies
  the tick and rebuilds the snapshot, the done task drops out (only open tasks are listed).
- **Why a tap Activity:** a collection has one tap template, and event rows must still open
  the app. A broadcast receiver can't reliably start the app (background activity start
  limits), so every Calendar row tap starts `CalendarTapActivity` (Theme.NoDisplay, empty
  `taskAffinity`, excluded from recents): a task row → queue the tick and redraw; any other
  row → start MainActivity with the row's `lifeboard://open/...` link. Both new activities
  are `exported="false"` (only the widgets' own PendingIntents start them) and use an empty
  task affinity so the app's task isn't brought forward.
- **App side:** `applyWidgetQueues` (src/app/widgets.ts, replaces `applyWidgetTicks`) takes
  each queue (read, remove, parse) and applies list ticks → `setTodoItemDone`, adds →
  `addTodoItem`, task ticks → `setTaskDone`, all through `call()`. In `main.ts` the
  `setAfterPhoneCall` hook is now set **before** the queues are applied at start, so a
  widget task tick reschedules reminders and runs `refreshSchedule` (Google push when away
  from the desktop) exactly like an in-app tick. Resume applies the queues too.
- Same small race as list ticks (a change made between the app reading and removing a
  queue is lost).

## Gotchas
- `adb shell am force-stop` cancels the app's PendingIntents, so widget taps do nothing
  until the widgets are redrawn (open the app once). Use `am kill` after going home to
  simulate Android killing the app.
- Long-press on the Pixel launcher: `input swipe x y x y 1500` didn't register; use
  `adb shell "input motionevent DOWN x y; sleep 1.5; input motionevent UP x y"`.
- After `adb install -r` the placed widgets draw blank until the app runs once.
- Driving the WebView for test setup: raw CDP (see the LAN sync note); the phone database
  is `lifeboard` for `CapacitorSQLite.query`.
- The first tap on a just-placed widget only takes the launcher out of edit mode.
- Android string resources need apostrophes escaped (`\'`); XML comments can't hold `--`.
