# Schedule: Google Calendar + Google Tasks (plan phases 5 and 6, combined)

2026-10-16, agent (Claude). Built against a pretend Google (test/schedule.test.ts); **not yet
run against the user's real account** (needs a new Google sign-in with the added scopes, and
the Calendar and Tasks APIs enabled in the Cloud project).

## User decisions (2026-10-16)
- One Schedule page (Details → Schedule): every day has a header with +, scrolls back and
  forth without end, opens at today, floating "Today" button when today is off screen.
- Per day: **tasks, then all-day events, then timed events**.
- Tasks: completable on screen; **done tasks stay crossed out**; **overdue open tasks show on
  today, highlighted**; tasks may have a **Lifeboard-only time** (Google Tasks keeps dates only).
- Calendars: **main only**, with Settings → Calendars to add others. Task lists: all shown.
- Repeating events: edit/delete "this", "this and following", "all".
- Hub → Lists stays separate from Google Tasks. Reminders/notifications: later.

## How it works (core/schedule/)
- `repeat.ts`: form repeat ↔ RRULE (subset: daily/weekly+days/monthly/yearly, interval,
  never/until/count). Anything else round-trips untouched as `custom`. `nextTaskDue` for
  repeating tasks (Tasks API has no recurrence: Lifeboard keeps the rule on the open task;
  ticking it creates the next task and moves the rule there).
- Tables (migration 9, all synced): `calendar`, `task_list`, `calendar_event` (occurrences,
  plus `is_series` rows holding each series' recurrence), `task`, `schedule_change` (queue).
- `edit.ts`: every edit updates rows at once and queues an op in `schedule_change`. The
  phone queues too; LAN sync carries it to the desktop, whose `/sync` handler then pushes.
- `push.ts` (`syncSchedule`): only where a Google credential exists. Sends the queue in
  order, then re-reads Google (only when the queue is empty) and replaces rows within
  365 days back / 730 ahead. **Google wins**: before patch/delete, the item's current etag
  is compared with the edit's base etag; mismatch → op dropped + built-in alert
  (`recordAlert`). Etags produced earlier in the same run are accepted (two queued edits
  to one item). A failed request stops the run; the rest retries next time.
- Rows match Google by `google_id`, so a row made locally keeps its id after creation. A new
  *repeating* event's local row is deleted after insert; its occurrences come with the re-read.
- "All events" moves the series by as many days as the user moved this occurrence;
  "this and following" sets UNTIL just before the occurrence (COUNT removed) and inserts a
  new series from the form. First occurrence → treated as "all".
- Runs: Google integration's 4-hourly update, Schedule open (`refreshSchedule`), after each
  edit (background), after a phone sync arrives with queued changes.

## Known limits
- Multi-day all-day events keep their length when edited but the form can't change it.
- Timed events show only on their start day.
- A phone edit of a series only changes the occurrence on screen until the desktop pushes
  and the phone syncs again.
- Google sign-in scopes now include calendar.calendarlist.readonly, calendar.events, tasks:
  an old sign-in gets 403 → "Google needs a new sign-in" (signed_out).
- Integration renamed "Google Health" → "Google" (connection row name updates on next run).
