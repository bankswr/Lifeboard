# LAN sync (plan phase 2)

2026-10-15, agent (Claude). Built while the user was away; design follows docs/PLAN.md
(data only, newest edit wins per record, phone starts every sync).

## How it works
- Code: `src/core/sync/records.ts` (synced-row bookkeeping), `src/core/sync/sync.ts`
  (the exchange), desktop `POST /sync` in `src/desktop/server.ts`, phone client
  `src/app/sync.ts`. Long explanation is in the header comment of `sync.ts`.
- **A feature makes a table synced by** creating it with `${syncColumns}` and pushing its
  name onto `SYNCED_TABLES`, then writing rows only via `saveRecord` / `deleteRecord`.
  Deletes are tombstones (`deleted = 1`); queries must filter `deleted = 0`.
- "Changed since last sync" uses per-device change numbers (`seq`, `meta.next_seq`), not
  timestamps, so clock skew can't make rows get skipped. Timestamps only decide which
  version wins. `saveRecord` stamps at least 1 ms after the row's previous `updated_at`, so
  a local edit beats the version it replaced even if this device's clock is behind.
- Echo: rows a device just received get a new local seq and are sent back next time; the
  other side ignores them (not newer). Settles after one extra round (tested).
- The phone tracks one desktop (`meta.sync_peer_id` + `sync_peer` row). If a different
  desktop answers (other machine, reset DB), it re-sends everything from seq 0.
- Incoming table/column names are checked against `SYNCED_TABLES` and `pragma_table_info`
  before going into SQL.

## Security / network decisions
- Desktop server now listens on `0.0.0.0` by default (was 127.0.0.1). Other machines can
  only reach `POST /sync`, which needs the sync key (`Authorization: Bearer <key>`,
  constant-time compare). Everything else (UI, `/api`, `/desktop/pairing`) answers loopback
  only. `LIFEBOARD_HOST=127.0.0.1` turns LAN sync off.
- The sync key is made once per desktop DB (`meta.sync_key`) and shown on the desktop's
  Settings screen with its LAN addresses. On the phone, `meta.sync_key` holds the key the
  user typed and `meta.desktop_address` the address — same key name, different role.
- Plain HTTP on the LAN (no TLS): someone on the home network could read synced data in
  transit. Accepted for now; revisit if credentials or sensitive data ever sync (they
  don't: credentials are per device).
- Android: `CapacitorHttp` is enabled (fetch goes native: no CORS, and `http://` from the
  `https://localhost` WebView works) and `usesCleartextTraffic="true"` is set in
  AndroidManifest.xml (Android can't scope cleartext to private IPs).
- If the desktop has a firewall (ufw) enabled, port 5180/tcp must be allowed for the phone.
  Not checked (needs root).

## When sync runs
- Phone: on app open (quietly; failures only logged, the desktop may just be off) and via
  Settings → "Save and sync now". No background sync (user decision).
- Since 2026-10-18 (user): also every 30 minutes while the app is open (`startPeriodicSync`
  in `src/app/sync.ts`), skipped when `navigator.onLine` is false; on resume it syncs if
  30 minutes have passed, since WebView timers pause in the background. Still nothing while
  the app is closed (user chose this over WorkManager-based background sync).

- Since 2026-10-20 (user): each request to the desktop times out after 15 s
  (`SYNC_REQUEST_TIMEOUT_MS`), and sync is skipped when `navigator.onLine` is false. Away
  from home the LAN address never answered, and since sync runs in the phone's `onPhoneDb`
  queue, the app hung on "Syncing with the desktop…" with every call stuck behind it. The
  timeout is a `Promise.race` as well as an abort signal, in case Capacitor's native HTTP
  ignores the signal. Verified on the emulator against an unroutable address
  (10.255.255.1): the banner cleared and the app carried on.

## Verified
- 12 tests (`test/sync.test.ts`: both directions, conflict, tombstone, settling, desktop
  change, rejection of unknown tables/columns, clock-behind stamping).
- Emulator (`fitapp_test`) → desktop LAN IP: wrong key → "The desktop rejected the sync
  key."; right key → "Synced: sent 0, received 0." (no feature tables exist yet). From the
  LAN IP, `/api/*` and `/` → 403; `/sync` without key → 401.
- Driving the WebView: Playwright `connectOverCDP` fails on Android WebView ("Browser
  context management is not supported"). Raw CDP works: `adb forward tcp:9333
  localabstract:webview_devtools_remote_<pid>`, then `Runtime.evaluate` over Node's
  built-in WebSocket (script pattern in this note's session; easy to rewrite).

## Update (same day): phone operations are serialized
- On the phone every API call and sync runs through one queue (`onPhoneDb` in
  `src/app/backend.ts`). Capacitor DB calls are truly async, so without it a UI write during
  a sync would join the sync's transaction (the adapters' "nested call joins the outer
  transaction" rule can't tell nested from concurrent) and be lost on rollback.
- Cost: UI actions wait while an update's network requests run (seconds, on open or
  "Update now"). Never call `call()` from inside an `onPhoneDb` operation: it would wait on
  itself forever.
- Desktop doesn't need it: node:sqlite is synchronous, and no transaction awaits network.
